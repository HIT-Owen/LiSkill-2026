# Design notes — from the paper to the code

This document walks through the pipeline in the order of §3 and names the
function that implements each definition, equation and table.

```
platform APIs ──collect──▶ raw records ──clean──▶ LiSkill-825k (unique skills)
                                                      │
                            ┌─────────────────────────┴──────────────────┐
                            ▼                                            ▼
               licence reference set (4,996)                 skill packages on disk
                            │                                            │
                       term database ◀── reader ──┐               extract (3 levels)
                            │                     │                      │
                            │              licence texts          skill_licenses docs
                            └──────────────┬─────────────────────────────┘
                                           ▼
                                 LST  /  SCC  ──▶ conflicts
```

## §3.1 Collection and preprocessing

| step | code |
| --- | --- |
| platform declarations (endpoint, paging, rate limit) | `data_collection_preprocessing/skills/platforms.py::PLATFORMS` |
| list parsing per market | `data_collection_preprocessing/skills/spiders.py::PARSERS` |
| HTTP with retry, back-off, rate limit, proxy env | `data_collection_preprocessing/skills/http.py::HttpClient` |
| cursor checkpoint / resume | `data_collection_preprocessing/skills/sink.py::CursorStore` |
| Invalid Record Filtering | `data_collection_preprocessing/skills/clean.py::is_valid_record` (name, description, ≥50-char body) |
| Cross-platform Deduplication | `data_collection_preprocessing/skills/clean.py::deduplicate` (SHA-256(name+description), earliest timestamp, hash becomes `skill_id`) |
| Data enrichment | `data_collection_preprocessing/skills/enrich.py::GitHubEnricher` (`repo_license`, package archive, `SKILL.md`) |
| storage | `data_collection_preprocessing/skills/sink.py::JsonlSink` / `MongoSink` |
| SPDX licence corpus (list + full texts) | `data_collection_preprocessing/licenses/spdx.py::crawl` (`liskill cli spdx`) |
| reference set assembly | `data_collection_preprocessing/licenses/reference.py::build_reference_set`, `data_collection_preprocessing/licenses/spdx.py::build_reference_set` |

Seventeen markets are declared. Three need more than a list-and-page loop and say
so in their declaration: `skillsmp` sets `keyword_param`/`keywords` (its search
API rejects an empty query), `skills.rest` sets `detail` (its sitemap yields
pointers that the runner resolves), and `awesome-agent-skills` sets
`paging="single"` (one page carries the whole catalogue).

The demo corpus is generated by `demo/corpus.py::build_synthetic_ecosystem`,
which writes real packages so that the extraction stage parses files rather than
a fixture table.  The released 1,484-skill sample in
`data/agent_skills/skills_demo.jsonl` is a random draw from the full 6.2 GB dump,
which stays outside the artifact.

## §3.2 Extraction and normalization

Three carriers, three extraction routines (`extract/layers.py`):

| level | source | routine |
| --- | --- | --- |
| Repository | `repo_license` from the GitHub API, else a `LICENSE` file in the repo archive | `extract_repository_level` |
| Skill | `license:` in the SKILL.md frontmatter, else `LICENSE`/`COPYING`/`NOTICE` at the skill root | `extract_skill_level` |
| Component | head comment (20 lines) of every text file under `scripts/`, `references/`, `assets/` | `extract_components` |

Normalization (`extract/normalize.py`) follows §3.2.2 exactly:

1. **rule pre-filter** — `ReferenceSet.match_exact` normalises case, hyphens and
   spaces, so `GPLv2`, `GPL-2.0` and `GPL 2.0` all collapse to `GPL-2.0-only`;
   declarations with a connector, natural language or an indirect reference skip
   the filter;
2. **model** — Appendix A (`extract/prompts.py`) with the closed candidate set,
   answered by the local base Qwen3.5-9B (`LLMConfig.for_normalization`);
   `parse_model_answer` enforces R1–R3 and rejects invented identifiers;
3. **indirect declarations** — `resolve_refer_local` (full-text SHA-256 first,
   model name lookup second, custom registration third) and `resolve_refer_repo`
   (collected repository licence);
4. **custom registry** — `ReferenceSet.register_custom` allocates `LIC-XXXX`
   deterministically from the declaration hash and stores
   `source = skill-declaration`.

Every level yields a Table-6 record; the per-skill document is
`schema.py::SkillLicenseDoc` (§3.2.3).

## §3.3 License understanding

| step | code |
| --- | --- |
| sentence segmentation | `understand/reader.py::split_sentences` |
| eq. (2) near-duplicate removal (cosine ≥ 0.95) | `understand/dataset.py::dedupe_sentences` over `understand/embedding.py::QwenEmbeddingEncoder` |
| pre-annotation + 7:1:2 split | `dataset.py::pre_annotate`, `split_samples` |
| Appendix B prompt / training pair | `understand/prompt.py` |
| eq. (1) inference | `reader.py::HeuristicLicenseReader.read_sentence`, `LLMLicenseReader` |
| eq. (4)(5) LoRA fine-tuning | `understand/train_lora.py::train` |

Three models, never interchanged. §3.3.3 reading and the §3.4.1 term database
address the *fine-tuned* checkpoint — `LLMConfig.model = "Qwen3.5-9B-LiSkill"`,
the adapter written by `train_lora.py` under `out/qwen3.5-9b-liskill-lora`, with
the base id `Qwen/Qwen3.5-9B` appearing only as the starting point of training.
§3.2.2 declaration normalisation uses `LLMConfig.for_normalization()` — the *base*
Qwen3.5-9B, served locally under its own name, because the task is a closed-set
choice that needs no fine-tuning. §3.3.2 pre-annotation and the §4.4.2 workflow
generation use `LLMConfig.for_drafting()` (DeepSeek-V4-Flash-0731, official API,
reasoning effort high, vendor default decoding — §4.1.4).

`HeuristicLicenseReader` is the dependency-free implementation used by the demo.
Its decisions are explicit and reviewable:

* a clause is the unit of modality scoping (`split_clauses`);
* a conditional prohibition (`may not … without … permission`) is `MUST` (R6);
* a right granted *before* a `provided that` condition stays `CAN`, because the
  condition belongs to the obligation that follows;
* guards in `ontology.py` suppress well-known false positives (a "modified files
  must carry notices" clause is T19, not a restriction on T2).

`QwenEmbeddingEncoder` (eq. (2)) follows the model card: sentences are encoded as
*documents* — de-duplication compares sentences with each other, so no prompt is
applied — while `encode_queries` exposes the `query` prompt for retrieval callers.
`--use-embedding` swaps it in; the default stays the n-gram stand-in, and the
weights load only on the first `encode_*` call.

## §3.4 Conflict detection

**Term database** (`conflict/termdb.py`). Sentence observations `O_l(t)` (eq. 6)
come from the reader handed to the constructor — `LLMLicenseReader` when the
pipeline was given a client (`liskill termdb --use-llm`), the offline heuristic
reader otherwise. They are folded by `strictest` (Table 7 A3), then completed by
the default rules:

* D1 — unmentioned obligations (T19–T31) default to `CAN`;
* D2/D3 — unmentioned rights default to `CAN` when `Grant(l) = 1`, else `CANNOT`.

`Grant(l)` is the catch-all cue of Table 7 (`without restriction`, `for any
purpose`, `perpetual`, …). A licence that instead enumerates at least two
right-class terms with `CAN` is treated the same way, so D3 keeps firing only on
declarations that say nothing.

**Intra-skill** (`conflict/lst.py`). `build_lst` maps the three levels onto a
rooted tree, skipping non-`Valid` levels so an edge may cross layers; labels
propagate downwards and a Skill-level declaration overrides the inherited
repository licence. Multi-AND nodes aggregate by ⊙; Multi-OR nodes are evaluated
per alternative and the edge only conflicts when *every* alternative conflicts.

**Inter-skill** (`conflict/scc.py`). `SkillCompositionChain.edges()` yields
`(index, consumer, producer)` from the innermost edge outwards, i.e. the root is
the chain tail. Node licences resolve Skill level → Repository level → missing.

**Edge judgement** (`conflict/matrix.py`). `judge_term` implements eq. (10) over
Table 8; `Depends` is resolved by `conditions_compatible`, which compares the
condition text extracted from the two evidences and reports exclusivity only when
one side negates what the other demands.

## §4 Evaluation

`eval/metrics.py` implements eq. (13)–(15) on *multisets* of `(term, attitude)`
pairs (repeated terms are matched one by one) plus the detection reporting units
(#Report, FPR, FNR). `eval/rq.py` aggregates RQ1 coverage, licence composition,
and the conflict scale/shape for both classes; `report.py` renders them.

**Workflow generation (§4.4.2).** An agent's planning trace cannot be observed,
so the evaluation chains come from task requirements.
`demo/workflows.py::LLMWorkflowGenerator` asks DeepSeek-V4-Flash-0731 for
realistic requests per functional category, recalls candidates by matching the
requirement against skill name/description (`recall_skills`), then asks the same
model for the minimal skill set in activation order (`compose`, and
`parse_skill_order`, which drops any identifier outside the recall). A
requirement that resolves to a single skill produces no call edge and is
discarded, as §4.4.2 states. `build_workflows` in the same module is the seeded
offline stand-in that `liskill demo` uses.

## Design decisions worth flagging

1. **Compatibility-relevant terms.** Table 8 is applied over the 13 terms of
   `CONFLICT_TERMS`. A parent that permits and a child that requires the same
   *formality* (notice, file marking, disclaimer) do not make a distribution
   impossible — the obligations stack — so those terms stay in the ontology and
   the audit trail but not in the compatibility judgement.
2. **Undetermined composition edges.** An edge touching an undeclared skill is
   reported as undetermined instead of being resolved by rule D3 to `CANNOT`,
   which would flag every workflow containing an unlicensed skill.
3. **Deterministic reader.** The released reader is a lexicon + modality
   implementation, not the fine-tuned model. It exists so the pipeline is
   auditable offline; the model path (`--use-llm`) is the production one.
